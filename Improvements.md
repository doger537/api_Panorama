# Программа улучшений TTKMap

Основание: [Audit.md](Audit.md), коммит `8a8d33e`, 24.10.2026. Этот документ описывает **предлагаемые изменения**, а не выполненные исправления. Он дополняет аудит конкретным устройством модулей, очередностью работ и критериями готовности. Действующие AGENTS, API и задача-борд этим документом автоматически не изменяются.

## 1. Какой результат нужен

Организатор должен пройти через реальные экраны путь: вход → новая карта → план → POI и граф → съёмка или загрузка панорам → их размещение и переходы → публикация. Посетитель должен открыть постоянную ссылку или iframe, построить путь, пройти его в панорамах при достаточном покрытии и увидеть сохранённые изменения.

Улучшения оцениваются по трём результатам:

1. **Функциональная полнота:** сценарий завершается без SQL, ручного JSON и имитации успеха.
2. **Поддерживаемость:** у каждого состояния, преобразования и правила есть понятный владелец и одна рабочая реализация.
3. **Скорость разработки:** небольшое изменение проходит понятный цикл проверки без ручного согласования каждого файла и дублирования статусов.

Существующие React/TypeScript, FastAPI/Python, SQLite и Hugin подходят для этого MVP. Основные изменения — внутри приложения и процесса поставки. Добавление отдельной СУБД, брокера и новых сервисов стоит обосновывать измеренной нагрузкой, а не самим наличием технического долга.

## 2. Архитектура: границы по ответственности

### Frontend

Целевая структура ниже — ориентир для постепенного рефакторинга, не требование создавать все файлы сразу:

```text
frontend/src/
  app/
    App.tsx                    # композиция экранов и провайдеров
    routes.tsx                 # реальные URL и guard организатора
    SessionProvider.tsx        # серверная сессия и её lifecycle
  shared/
    api/                       # HTTP, error envelope, CSRF, transport DTO
    geometry/                  # координаты плана и углы панорам
    ui/                        # общие доступные элементы интерфейса
  features/
    organizer/
      pages/                   # login, список карт, workspace
      workspace/               # draft, revision, assets, сохранение
      share/                   # publish, URL, безопасный iframe snippet
    plan/
      canvas/                  # SVG и преобразование pointer coordinates
      tools/                   # select, wall, room, corridor, POI, graph
      model/                   # операции над документом и undo/redo
      inspector/               # поля выбранной сущности
    capture/
      camera/                  # stream, video, кадр, датчики
      session/                 # создание/восстановление/завершение capture
      uploads/                 # pending frames, ack, retry
      job/                     # polling, cancel, импорт результата
    panorama/                  # viewer, варианты медиа, hotspot editor
    visitor/                   # public snapshot, план, маршрут, walkthrough
  demo/                        # явно включаемый демонстрационный режим
```

Правила зависимостей:

- `app` собирает feature-модули, но не содержит алгоритмов редактора, маршрута и съёмки.
- `shared` не импортирует feature-модули и не содержит демо-пространства или копии предметных сущностей.
- Feature предоставляет небольшой публичный интерфейс. Общение между редактором, capture и panorama идёт через workspace и callbacks/команды, а не через внутреннее состояние соседнего компонента.
- Transport DTO импортируется из общего контракта. UI-модели допустимы для представления, но не превращаются во второй независимый формат карты.
- Сложные переходы используют typed reducer и явные события. Простое локальное состояние остаётся в `useState`; глобальное хранилище для всего приложения не требуется.
- Асинхронный ответ применяется только к тому map/session/request, для которого он был запрошен. При смене контекста запрос отменяется или его результат игнорируется.

`App.tsx` уменьшается за счёт передачи обязанностей, а не механического переноса функций в файл `utils.ts`. Для небольшого MVP можно подключить существующий Router, добавить корректный `popstate` и guard. Рабочие маршруты: `/login`, `/organize`, `/organize/:mapId`, `/m/:slug`, `/embed/:slug`; существующий `/edit` должен иметь понятный переход для совместимости.

### Backend и worker

```text
backend/app/
  main.py                      # создание приложения и подключение роутеров
  routers/                     # HTTP, зависимости доступа, request/response
  modules/
    maps/
      service.py               # операции карты, транзакционная граница
      validation.py            # геометрия, ссылки, readiness
      snapshots.py             # organizer/public DTO из согласованного чтения
      repository.py            # повторно используемые SQL-операции
    media/
      service.py               # приём, нормализация, создание вариантов
      images.py                # единственная политика обработки изображений
      storage.py               # staging, immutable files, атомарная запись
    capture/
      service.py               # сессии, слоты, постановка/отмена jobs
      uploads.py               # ограниченное чтение входящих данных
    routing/
      graph.py                 # Dijkstra и условия panorama walk
backend/worker/
  main.py                      # запуск consumer
  coordinator.py               # claim, heartbeat, cancel, commit/failure
  stitching.py                 # единственная Hugin pipeline
  quality.py                   # измерение покрытия и проверка результата
```

Роутер не импортирует приватную функцию другого роутера. Транзакцией бизнес-операции владеет service; repository не делает неожиданный commit. CPU-обработка изображения и файловые операции подготовки выполняются вне длительной writer-транзакции. Публичный snapshot собирается согласованно и отдельным whitelist DTO. Не следует вводить универсальные repositories, абстрактные factories и дополнительные слои для каждой простой функции: выделение оправдано повторным использованием или отдельным инвариантом.

Сохраняются важные решения: один источник геометрии карты, atomic document replacement, immutable slug/extents, optimistic concurrency, authorization-aware media и worker вне HTTP.

## 3. Редактор и сохранение

### Управление документом

Workspace становится владельцем `mapId`, `baseRevision`, последнего подтверждённого документа, редактируемого draft, asset registry и состояния сохранения. Состояния: loading, ready, dirty, saving, conflict, error. Производные значения вычисляются из этих данных, не хранятся в нескольких несогласованных копиях.

При сохранении фиксируются отправленный документ и версия локальных правок. Успешный ответ обновляет базовую revision, но не затирает изменения, появившиеся во время запроса. Для первого исправления достаточно блокировать повторный save и корректно удерживать новые dirty edits; сложное автоматическое слияние не требуется.

Ответ 412 сохраняет локальный draft. Интерфейс предлагает загрузить серверную версию либо осознанно повторить запись после просмотра различий и получения нового ETag. Нельзя автоматически подставлять новую revision и молча перезаписывать чужой документ. Publish/unpublish считается завершённым только после подтверждения сервера. При переключении карты пользователь сохраняет, отбрасывает или продолжает редактирование.

### Инструменты плана

Минимально законченный editor включает:

- Выбор и перемещение объектов; редактирование/удаление стены и вершин room/corridor.
- Создание произвольных полигонов и отрезков, а не только фиксированных прямоугольников.
- Полный inspector POI: title, category, category_label, description, position и access node.
- Явное создание/удаление nodes и edges; выбор концов прохода. Автосвязь ближайших POI не должна становиться обязательным графом.
- Panorama inspector: положение, связанный узел, heading, asset и удаление с очисткой зависимых hotspots.
- Undo/redo для локальных операций документа; объём истории ограничен. Это снижает цену ошибки при touch editing.

Преобразование pointer coordinates выполняется через обратную SVG screen CTM. Масштабирование и перемещение viewport не меняют координаты документа. Подложка отображается из AssetRef одинаково после upload, reload и в public view; изображение не получает отдельную несохраняемую деформацию в canvas.

Геометрический валидатор проверяет bounds, вырожденные сегменты, простоту полигонов и ссылки. Граф маршрутизации задаётся организатором: автоматическое распознавание стен остаётся backlog. Предупреждение о пересечении стены допустимо как помощь, но не заменяет явное моделирование дверей/проходов.

**Готово, когда:** импортированный план и его маркеры совпадают после reload и в public view; комнату можно изменить, POI перенести и переименовать, а маршрут провести вокруг препятствия через заданные проходы. Связь с аудитом: A05–A08, A15.

## 4. Съёмка, загрузка и склейка

### Камера и capture session

Поток камеры существует независимо от экрана preview. Video сохраняется смонтированным или получает `srcObject` на каждом mount. Снимок разрешён только после готовности video; вместо пустого/синтетического кадра показывается причина отказа. Размер уменьшается с сохранением aspect ratio. Направление гида отсчитывается от начальной ориентации, а недоступность датчика не блокирует ручную съёмку.

Разрешение iOS на датчики запрашивается из пользовательского gesture. Отдельно обрабатываются запрет камеры, потеря stream, background/foreground, смена orientation и закрытие экрана. Stream и object URLs освобождаются при завершении. Capture получает актуальные map document/extents от workspace.

UI-фазы камеры и серверные состояния job — разные модели. Новая серия всегда получает новый capture ID после terminal state; retry failed job использует существующий ID и серверный лимит попыток. Смена mapId сбрасывает контекст предыдущей карты.

Pending frame хранится до подтверждения загрузки. Для восстановления после перезагрузки можно использовать небольшую IndexedDB-очередь: mapId, captureId, index, File, состояние отправки. Подтверждённые файлы удаляются, размер очереди ограничен и виден пользователю. Это устойчивость операции съёмки, не обещание полноценного offline-продукта.

После восстановления клиент сверяет реальные серверные слоты и досылает отсутствующие. Для 16 готовых кадров есть самостоятельная кнопка повторной постановки stitch. Импорт succeeded asset в документ идемпотентен по capture/result asset и повторяется при ошибке сети. Съёмка не считается добавленной в карту до подтверждённого сохранения документа.

### Один worker pipeline

Coordinator получает job, запускает единственную pipeline и отвечает за её lifecycle. Пример исходной настройки для проверки: lease 120 с, heartbeat каждые 20 с; окончательные значения уточняются по измерениям. Общий deadline job и лимиты отдельных команд задаются конфигурацией.

Каждое изменение progress/result проверяет в одной SQL-операции состояние running, текущий lease token и неистёкший срок. Heartbeat использует своё корректно созданное SQLite-соединение. Потеря lease запрещает commit результата. Cancel завершает группу дочерних процессов и освобождает временные ресурсы. Ошибку запуска/декодирования/качества нельзя преобразовывать в success.

Успех требует измеримого результата: достаточных соответствий кадров, замыкания полного оборота, достаточного непрерывного покрытия и корректных crop/offset. При 360° по горизонтали и сферическом canvas согласованность `width`, `height` и `vaov` проверяется явно; `180°` не подставляется константой. Порог числа control points и alpha coverage калибруется по реальным положительным/отрицательным сериям, а не объявляется универсальной гарантией качества шва.

Файловая система и SQLite не образуют общую атомарную транзакцию. Поэтому нужен явный протокол: подготовить проверенные immutable файлы → завершить их запись → коротко проверить lease и создать DB references → подтвердить success. При сбое остаются только недоступные пользователю сироты, которые удаляются GC после защитного интервала и проверки активных операций.

**Готово, когда:** 16 кадров снимаются без потери stream; retry не требует ненужной пересъёмки; cancel/new и success/new работают; положительная серия даёт корректные измеренные metadata, отрицательная остаётся failed; две копии worker не завершают одну lease одновременно. Связь: A01–A04, A07, A11.

## 5. API, данные и контракты

- Сохранить `CONTRACTS/openapi.yaml` источником transport contract и генерировать из него `types.ts` фиксированной версией генератора. Ручные UI-адаптеры держать отдельно от generated DTO.
- Сверять действительные request/response/error/status codes с OpenAPI в интеграционных тестах. Дополнить контракт фактическими ограничениями размеров/строк/форматов. Генерация TypeScript сама по себе не проверяет Python runtime.
- Добавить response models для HTTP-ответов или явные проверяемые serializers, особенно для public DTO. Не отдавать `SELECT *` непосредственно клиенту.
- Переводить ожидаемые integrity conflicts в документированный 409/422 с полезным полем issues. Не раскрывать владельца чужого UUID. Не менять статус существующей операции без синхронного обновления потребителя и теста.
- Добавить pagination карт/ресурсов, когда список может превышать лимит; текущий `LIMIT 100` не должен скрывать старые карты без способа их получить.
- Оформить versioned migrations и backup/restore. Запуск на существующей неподходящей версии должен завершаться понятной ошибкой; init schema остаётся только для пустой БД.
- Добавить контролируемую очистку sessions, raw frames и сирот assets. Retention задаётся конфигурацией; GC имеет dry-run и исключает действующие ссылки, uploads и jobs.
- Определить readiness публикации: обязательные ошибки блокируют, отсутствие панорамного покрытия даёт понятное предупреждение. Не требовать panorama walk для каждой карты, если граф/панорамы ещё не позволяют его построить.

**Готово, когда:** реальный API проходит schema validation, rollback сохраняет прежний документ, error codes понятны frontend, backup восстанавливается в отдельную БД, а GC не удаляет используемые медиа. Связь: A15, A18–A20.

## 6. Безопасность и обработка медиа

В рабочем приложении успешный вход определяется только server session; убрать локальные admin passwords, fallback login и псевдорегистрацию. Logout сообщает о неудавшемся отзыве сессии и позволяет повтор. Demo seed доступен только при явно выбранном локальном режиме; production-конфигурация не создаёт предсказуемого организатора.

Исправить dummy password verification для неизвестных email. Rate limit должен учитывать реальную конфигурацию API-процессов и доверенных proxy, иметь ограниченный объём хранения и тест параллельных попыток. Существующие cookie/CSRF/Origin/ownership сохранить. Production startup проверяет HTTPS origin и secure cookie; liveness и readiness различаются по назначению.

Для media использовать общий streaming parser с лимитом до накопления тела и декодирования. Проверять действительное содержимое, размер, pixel count, EXIF orientation; удалять GPS/metadata при нормализации. CPU-обработку выносить в ограниченный thread pool либо отдельный обработчик с установленным пределом параллелизма. Лимит запросов на reverse proxy дополняет, но не заменяет проверку приложения.

Iframe snippet создаётся безопасным serializer с экранированием атрибутов. CSP/frame-ancestors задаются по маршрутам: публичный embed поддерживает внешнее встраивание, organizer screen защищён от него. Ввод пользователя не попадает в исполняемый HTML. Проверить собственный tooltip путь после обновления Pannellum.

Обновить зависимости по A17, проверить frontend и Python SCA, затем автоматизировать небольшие dependency PR. Рейтинг dev-server advisory не следует переносить на production API без анализа применимости. Для каждого исключения нужна конкретная причина и срок пересмотра, а не формальная отмена всей проверки.

**Готово, когда:** отказ доступа не превращается в успешный UI, слишком большой поток отвергается до полного чтения, приватные/отвязанные медиа не отдаются даже по ETag, embed проходит тест с кавычками в title, известные применимые advisory устранены. Связь: A09, A12, A14, A16–A17.

## 7. UX, доступность и публичный просмотр

- Оставить один рабочий public flow для произвольного slug. Каталог демо отделить от карты организатора; ошибка маршрута не рисует правдоподобный выдуманный путь.
- Показывать устойчивые состояния loading/error/empty/saving/conflict, а не только исчезающий toast. Повтор операции должен сохранять введённые данные.
- Выбирать panorama asset строго по ID. После upload обновлять asset registry workspace. Не подставлять другую сферу при недоступности нужной.
- Округлять yaw с повторной нормализацией; отображать только доступный pitch для измеренного охвата. Обрабатывать событие ошибки Pannellum и возможность повторной загрузки.
- При изменении revision сбрасывать устаревший маршрут и объяснять необходимость пересчёта. При 409 не сообщать «пересчитан», пока новый route response не получен. При unpublish закрывать карту и доступные внутри неё операции.
- Для walkthrough показывать следующий panorama step, направление перехода и причину недоступности прохода. Панорамный проход создаётся только из подтверждённых graph bindings и directed transitions.
- Убрать запрет browser zoom, дать полям/кнопкам доступные имена, обеспечить keyboard navigation и управление фокусом в модальных окнах. Основные touch targets — ориентир 44–48 CSS px. Для SVG-объектов предоставить доступный список/inspector.
- Проверить mobile layout с открытой клавиатурой, длинными названиями, landscape и медленной сетью. Предпросмотр, retake и cancel должны оставаться доступны одной рукой.

**Готово, когда:** пользователь различает сохранённый результат, локальный draft и ошибку; карта работает без демо-каталога; ключевые действия доступны с клавиатуры и на телефоне. Связь: A05–A09, A13–A14, A20.

## 8. Качество кода и тестовая стратегия

### Статические проверки

Для Python — Ruff check/format и постепенная проверка типов на границах service/DTO/worker. Для TypeScript — ESLint с hooks rules, strict typecheck, единое форматирование. Не подавлять dependencies effects без объяснения lifecycle. Пойманная ошибка либо преобразуется в явный результат, либо записывается с контекстом; `catch {}` допустим только для действительно необязательной операции.

Сначала применять правила к изменяемым модулям. Массовое форматирование всего репозитория вынести в отдельную механическую правку, если оно вообще понадобится. Количество строк файла и общий coverage не превращать в формальные цели: важнее число обязанностей, ясность API модуля и покрытие рискованных переходов.

### Какие тесты дают нужную уверенность

| Уровень | Что проверять | Где допустимы подмены |
|---|---|---|
| Чистые функции | Координаты/углы, операции графа, геометрия, reducers, выбор asset | Внешних сервисов нет |
| API integration | Настоящий SQLite, auth, ownership, document replacement, 412, media access, queue transitions | Внешняя тяжёлая обработка подменяется, если она не предмет теста |
| UI integration | Ввод пользователя, camera DOM lifecycle, dirty/save/conflict, retry и смена карты | API управляет ответами, но тестирует реальные компоненты и события |
| Worker integration | Настоящие Hugin/enblend, реальные fixtures, metadata/quality gate, failed cases | Не подменять pipeline, которую тест должен доказать |
| Browser E2E | Реальные frontend/API/SQLite; создание и публикация карты, route/walk, live update, unpublish, iframe | Детерминированная fake-camera может проверять браузерный поток; это отдельно от приёмки телефона |
| Device acceptance | iOS Safari/Android Chrome по HTTPS, реальные камера/датчики/WebGL/touch и сеть | Подмена устройства не допускается |

Дополнительные probes из аудита нельзя переносить как зелёные тесты, утверждающие дефектное поведение. Их нужно преобразовать в regression tests с правильным ожидаемым результатом.

Минимальные защитные сценарии: видео после review, cancel→new, upload retry с тем же slot, loss of lease, отсутствующий asset, yaw у границы ±180°, 412 в двух вкладках, поздний save response, смена карты во время запроса, unpublish до 304, rollback при invalid geometry, oversized streaming upload и внешний iframe.

Фикстуры должны иметь manifest с источником, разрешением использования, устройством или честной отметкой «неизвестно», порядком кадров, файлами и хешами. Добавить действительно наполненный unrelated набор и контрольный готовый результат. Синтетические fixtures пригодны для API, но не являются доказательством качества съёмки.

## 9. Сборка, CI/CD и эксплуатация

### Воспроизводимая разработка и поставка

Зафиксировать поддерживаемые Node 22/Python 3.12 в локальной конфигурации и CI. Использовать `npm ci`, backend lock с hashes и один способ обновления прямых/транзитивных зависимостей. Устранить Windows-зависимость build wrapper от запуска `.cmd` через `shell:false`.

Рекомендуемая поставка для текущего масштаба: сборка Vite в Node stage, API image со статическим dist и runtime Python, отдельный worker image с Hugin/enblend. Общий reverse proxy обеспечивает HTTPS и один origin для страниц/API. Hugin не требуется в API image. Для frontend не нужен отдельный долгоживущий Node dev-server. Tailwind собирается локально, критические стили не зависят от CDN script.

API и worker используют согласованные настройки и общий persistent media/SQLite volume. Контейнеры получают restart policy, ограничение ресурсов, пользователя без root там, где это совместимо с volume permissions, и корректную остановку. В README описываются создание organizer, initial DB, обновление, backup/restore и HTTPS-доступ с телефона.

### Проверки CI

1. Быстрый слой: форматирование, типы, contract drift, нужные unit/API/UI tests.
2. Сборка реально поставляемых images и smoke HTTP/static assets. Тестовый образ обязан содержать текущий checkout; старый локальный tag не является доказательством.
3. Browser E2E для изменений интеграции, контрактов, editor/capture/public paths и перед релизом.
4. Реальная склейка при изменениях worker/media/capture contract или их зависимостей и перед релизом; периодический прогон для обнаружения внешнего дрейфа.
5. SCA и контроль lockfiles; проверка миграции при изменении схемы.

Для важных общих изменений список проверок расширяется автоматически. Изменение текста не требует запуска всех Hugin-серий. Фильтры CI должны учитывать косвенные зависимости: shared client, контракты, сборка и lockfiles затрагивают несколько модулей.

E2E создаёт собственный Compose project, временные данные и аккаунты. Cleanup удаляет только ресурсы этого запуска. Рабочая база и пользовательские volumes не участвуют в тестах.

### Наблюдаемость и восстановление

Логи содержат request ID/job ID, операцию, длительность и error code; пользователь получает краткую ошибку без внутренних путей. Пароли, cookie, CSRF и содержимое изображений не логируются. Измеряются очередь, длительность stages, число failed jobs по причинам, API latency, storage usage и возраст старейшего job.

Readiness API отражает готовность обслуживать запросы, состояние worker/очереди видно отдельно. Доступность health не выдаётся за доказательство работоспособной камеры или склейки. Backup проверяется реальным восстановлением в отдельном окружении. GC сначала запускается в dry-run, с отчётом о потенциальном удалении.

### Предлагаемые измеримые цели

Это стартовые **цели**, не результаты аудита и не новые требования заказчика. Перед приёмкой зафиксировать устройство, runner, размер карты и профиль сети.

| Показатель | Начальная цель | Условие измерения |
|---|---|---|
| Появление рабочего 2D-плана | ≤2 с | Типичная MVP-карта, средний Android, 20 Mbit/s, RTT 50 ms, холодный cache |
| Первый интерактивный panorama preview | ≤3 с | Тот же профиль; сначала mobile/preview |
| Live update | ≤20 с | Активная вкладка и исправная сеть; текущий polling 15 с |
| p95 чтения snapshot/route | ≤300 ms | Согласованный dataset, 20 параллельных посетителей на зафиксированном сервере |
| Сохранность данных | Нет потерянных подтверждённых изменений | Conflict, crash/restart, cancel и повторные запросы |
| Stitching | Baseline и предел по реальным fixtures | Фиксированные CPU/RAM и кадры; отдельно качество и время, без обещания универсального SLA |

Для memory/CPU сначала снять профиль параллельных uploads и worker, затем установить лимиты и проверить отказ при их достижении. Оптимизировать измеренный узкий участок; Redis, Postgres и многосервисная архитектура не являются предварительным условием этих целей.

## 10. Правила разработки: меньше шагов, больше проверяемого результата

### Предлагаемая замена текущего процесса

- Один связный результат на PR. Он может включать feature, минимальный shared/wiring change и необходимые тесты.
- Task ID полезен для связи с планом, но не должен быть обязательным пропуском для любого исправления. Жёсткие per-task `allowed_paths` заменить ownership/review routing; пересекающуюся конкурентную работу координировать.
- Единственный источник статусов задач. Рекомендуется GitHub issue/PR lifecycle, а краткий roadmap — в документации. Если нужен машинный manifest, workplan генерируется из него; два ручных источника не поддерживаются.
- Статус завершения возникает при merge с выполненными критериями. Не нужен отдельный ручной commit на main для каждой галочки.
- Worktree/clone обязательны при одновременной работе нескольких исполнителей. Для локального одиночного отчёта не требуется отдельный checkout ради самой процедуры.
- Shared-code не закрыт до финальной «интеграционной задачи». Вертикальный срез подключается и проверяется вместе с feature.
- Изменение контракта и его потребителей оформляется одной связной правкой, если ими занимается один исполнитель. Координация нужна при несовместимости/параллельной работе, а не на любое изменение строки DTO.
- Review по риску: auth, БД, контракты, worker и потеря данных требуют независимого взгляда. Документация и простые обратимые UI-изменения проходят сокращённый процесс по политике команды.
- Публикация, сообщения команде, push и PR выполняются только в рамках выданной авторизации. Локальная работа не должна останавливаться ради повторного согласования уже разрешённого шага.
- Известный дефект вне текущего модуля фиксируется отдельной задачей или небольшой связанной правкой; альтернативная реализация ради обхода границ запрещает сама себя архитектурно.

Это предложения для изменения AGENTS/CI, а не разрешение текущим исполнителям игнорировать ещё действующие правила. Перевод процесса должен быть отдельной небольшой правкой с сохранением полезных защит main, данных, контрактов и чужих изменений.

### Короткое описание PR

Четыре пункта: какой пользовательский сценарий изменён; что изменено в реализации; чем проверено; какие ограничения остались. Для миграции/контракта дополнительно указать совместимость и восстановление. Искусственное расширение описания ради шаблона не нужно.

Готовность задачи означает: рабочий путь подключён, результат подтверждён релевантной проверкой, ошибка не маскируется успехом, сопутствующая документация актуальна. Число файлов/коммитов и наличие папки `features` сами по себе готовности не доказывают.

Практический порядок:

1. **Сразу:** U01–U04, U06, U08 и основа U15. Эти работы снимают блокировки процесса, запуска, камеры и worker. Обновление уязвимых зависимостей можно делать одновременно с U02, не ждать полной U14.
2. **Следом:** U05, U07, U09–U12. Завершить документ, устойчивую съёмку и редактирование. Архитектурное выделение выполнять вместе с соответствующими исправлениями, сохраняя работающий путь после каждого PR.
3. **До приёмки:** завершить U13–U17 и полный U15. Затем U18 с реальными устройствами и зафиксированными ограничениями.

Не начинать весь рефакторинг одним большим PR. При назначении работ в команде лучше разделять вертикальные результаты: workspace/editor, capture/worker, поставка/публичный просмотр/проверки. Владельцы общих интерфейсов договариваются о формате до пересекающихся изменений. Этот документ не запускает параллельных исполнителей автоматически.

Оценивать длительность в календарных днях без состава команды, доступных устройств и реального fixture acceptance преждевременно. Размер работы удобно уточнять после первого небольшого среза и измеренного цикла review/CI; ограничивать стоит объём одновременно начатых задач, а не скорость количеством обязательных формальностей.

## 12. Как понять, что улучшения сработали

Функциональная метрика — сколько обязательных acceptance scenarios проходит на реальном приложении. Архитектурная — можно ли изменить capture, editor или worker, не переписывая несвязанные состояния App и не создавая вторую pipeline. Эксплуатационная — восстановление после ошибки не требует ручного вмешательства в данные. Командная — сокращается время от небольшой правки до проверенного результата при сохранении защиты данных и контрактов.

Следующий аудит должен показать не просто больше тестов, а отсутствие конкретных A01–A20, единый рабочий путь каждой функции и подтверждённый полный MVP на телефоне. Backlog-функции можно планировать после этой точки отдельно.
