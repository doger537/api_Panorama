# Аудит TTKMap

Дата: **24 октября 2026 года**. Проверенный коммит: **`8a8d33e0a76ff764f690a089e51330302a2e1731`**.

## 1. Заключение

**Проект имеет рабочую серверную основу и несколько законченных модулей, но обязательный MVP пока не завершён. Главные проблемы находятся в интеграции интерфейса организатора, съёмки и worker.** Успешные unit/component tests сейчас существенно переоценивают готовность пользовательского сценария.

Называть весь репозиторий «спагетти» было бы неверно. Сервер разделён на небольшие роутеры, есть общие DTO, транзакции, защищённая выдача медиа и самостоятельный процесс склейки. Хорошо выделены логика публичного просмотра, математические функции и операции очереди. Однако **frontend в точке сборки приложения уже обладает признаками монолита состояния**, а часть выделенных модулей не используется рабочим путём выполнения. Разбиение по папкам здесь не всегда означает разделение ответственности.

Три препятствия для приёмки полного сценария:

1. После просмотра первого снятого кадра компонент камеры создаёт новый `<video>`, которому не назначает поток. Продолжение съёмки повреждено.
2. Worker действительно запускает Hugin/enblend, но записывает неверные параметры полученной панорамы и обходит имеющуюся отдельную проверку качества.
3. Собранный штатным Dockerfile образ не содержит frontend. В нём `/` и `/m/:slug` возвращают 404; комплект поставки веб-приложения не закончен.

Дополнительно не завершены полноценное редактирование плана и графа, привязка панорам к навигационным узлам, обработка 412-конфликта в приложении, восстановление съёмки после ошибок. Демонстрационные данные и имитации результата смешаны с рабочими экранами.

**Рекомендация: сначала закрыть один реальный сквозной сценарий на новой карте, затем расширять функциональность. Полная перепись проекта не нужна.** Существующие серверные механизмы и чистые функции стоит сохранить; интеграционные обязанности и управление состоянием необходимо переработать адресно.

## 3. Архитектура и качество кода

### Сильные стороны

- `backend/app/main.py` остаётся небольшим composition root и подключает реальные роутеры всех основных функций.
- `db.py` централизует соединения, FK, WAL, busy timeout и транзакции. Существующая база с неподходящей версией не пересоздаётся автоматически.
- Сохранение карты использует `BEGIN IMMEDIATE`, проверку `If-Match`, замену связанных сущностей и одно увеличение revision. Воспроизведение коллизии ID подтвердило rollback, хотя HTTP-ответ некорректен.
- Сервер проверяет владельца вложенных ресурсов, Origin и CSRF. Публичные DTO не включают владельца, пароль, сессию, исходные кадры и storage keys.
- Публикация проверяется до ответа 304. Публичная выдача медиа ограничена assets, прикреплёнными к опубликованной карте; снятие публикации закрывает доступ.
- `modules/capture/service.py` реализует устойчивую очередь в SQLite, фиксированные слоты, идемпотентную повторную загрузку, неизменяемые имена заменённых файлов, ограничение попыток и fencing по токену при смене владельца job.
- Dijkstra и построение panorama walk имеют понятные условия, детерминированный обход и явные причины gaps. Сервер не подменяет отсутствующий путь прямой линией.
- `PublicSpacePage`, `usePublicMap`, `model`, `PublicPlan` существенно лучше отделяют данные и представление, чем старый экран каталога.
- Pannellum загружается отдельным модулем; существуют preview/mobile/full и политика выбора качества. Hotspot labels формируются через `textContent`.
- TypeScript включён в strict mode, DTO импортируются из `CONTRACTS/types.ts`. Для чистых функций, ownership, очереди и публичной маршрутизации есть полезные отрицательные тесты.

## 4. Найденные проблемы и рекомендации

Приоритеты: **P0** — блокирует обязательный пользовательский сценарий; **P1** — исправить до приёмки/развёртывания; **P2** — следующий этап стабилизации. P0 в этом отчёте не является рейтингом уязвимости.

### A01 — P0. После первого кадра теряется поток камеры

**Воспроизведено компонентным тестом.** `CaptureGuide.tsx:233` присваивает `srcObject` только при `startCamera`. На этапе reviewing `<video>` заменяется изображением (`CaptureGuide.tsx:505`). После «Оставить кадр»/«Переснять» создаётся новый DOM-элемент video без привязки к `streamRef`.

Первое video получило поток; после review новый video его уже не имеет. При штатном encoder это усугубляется `CaptureGuide.tsx:45`: если видео не готово, код генерирует однотонный кадр вместо ошибки. Кроме того, любой исходный aspect ratio принудительно растягивается до 600×800, что искажает геометрию кадра и предположение о HFOV.

**Исправить:** сохранять video смонтированным либо назначать поток через callback ref/effect при каждом mount; ожидать готовности изображения; запрещать снимок без живого кадра; уменьшать кадр с сохранением пропорций. Проверка приёмки — 16 реально разных кадров, preview/retake после каждого, без подмены encoder в интеграционном тесте.

### A02 — P1. Жизненный цикл capture не завершён

**Повторное использование отменённой сессии воспроизведено; остальные пункты подтверждены чтением рабочего кода.** В `shootFrame` выбирается `activeCapture ?? ensureCapture()` (`CaptureGuide.tsx:270`), независимо от состояния существующей сессии. После cancel `activeCapture` остаётся заполненным. Новая съёмка использует cancelled capture; backend правильно запрещает её изменение. Для succeeded с 16 кадрами обработчик возвращается ещё раньше из-за `index >= TOTAL_FRAMES`.

`acceptFrame` удаляет локальный File/preview до успешной отправки. При ошибке кадр теряется и его нужно переснимать. Восстановление через `resumeUploads` зависит от `captureFrame`, передаваемого тестами; рабочий `AdminView` этот prop не передаёт. LocalStorage сохраняет ID сессии, но не очередь файлов. Если постановка последнего кадра на stitch завершилась сетевой ошибкой, в рабочем UI нет явного повторного submit для collecting с 16 кадрами.

На успехе polling сначала выставляет succeeded/idle и очищает сохранённую сессию, а уже потом запрашивает assets. Если `listAssets` упадёт, polling прекратится, панорама может не попасть в документ. При смене карты компонент также не сбрасывает старую activeCapture отдельным переходом состояния.

**Исправить:** явные состояния сессии, «Новая съёмка», сброс при смене карты, хранение pending frame до ack, повтор submit и отдельный повтор импорта готового результата. Отделить полезный тестовый seam от механизма восстановления реального пользователя. Проверить cancel→new, success→new, failed→retry/new, потерю сети на каждом последнем шаге и переключение карт.

### A03 — P0. Worker публикует панораму с неверным вертикальным охватом

**Воспроизведено настоящими Hugin/enblend в контейнере.** `backend/worker/main.py:87` запускает собственную цепочку команд. При записи asset (`:113`) всегда устанавливаются `haov=360`, `vaov=180`, `v_offset=0`. Контроль замыкания, alpha coverage и измерение охвата из `worker/stitching.py:44` не используются.

Серия `series_01` с 16 кадрами, уменьшенными до 600×800, дважды дала succeeded примерно за 31–32 с. Во втором запуске готовый WebP имел **4096×865**, положительный alpha примерно на **90,36%** пикселей и 724 строки с покрытием ширины ≥98%, но asset сообщал **180°** по вертикали. При сферической развёртке 360°/4096 px высоте 865 соответствует около **76,0°**, а не 180°. Это расчёт по разрешению заданного canvas, не независимая оптическая калибровка. Уже само несоответствие размеров и объявленного охвата подтверждает дефект.

Отрицательный набор `negative_duplicates` корректно завершился failed из-за enblend и не создал asset. Поэтому утверждение «worker всегда имитирует успех» неверно. Проблема — недостаточные условия признания успешного результата и неверная геометрия метаданных.

**Исправить:** оставить одну проверяемую pipeline; измерять coverage, crop и offset; проверять соседние кадры и замыкающий шов; записывать измеренный `StitchResult` в asset. Нельзя просто подключить существующий `stitching.py` без проверки: он предполагает определённые размеры TIFF, а поведение crop enblend надо согласовать с ним. Зафиксировать реальный интеграционный тест результата, а не только exit code процесса.

### A04 — P1. Worker не продлевает lease и не останавливает работу при cancel

**Подтверждено кодом.** `claim_next_capture` выдаёт lease на 120 с (`service.py:189`). Цепочка subprocess допускает суммарно до 660 с, heartbeat отсутствует, progress остаётся 5 до финала. При commit проверяются state/token, но не срок lease (`worker/main.py:107`). `_fail_capture` также не проверяет срок.

При нескольких consumers живая длинная задача может быть отдана второму worker и потратить попытку; при одном consumer истёкший lease не препятствует успешному commit. Cancel инвалидирует токен в БД, что полезно, но уже работающие процессы продолжают потреблять ресурсы. Файлы результата записываются до финальной проверки токена и могут остаться сиротами.

**Исправить:** coordinator с heartbeat, общей длительностью job, проверкой state/token/unexpired lease при обновлениях, управляемыми subprocess и остановкой группы процессов. Добавить тест длительной задачи с двумя consumers и cancel во время enblend. Измеренный короткий прогон A03 не заменяет эту проверку.

### A05 — P1. Импорт плана не сохраняет одинаковое представление в редакторе и у посетителя

**Подтверждено кодом.** `PlanEditor.tsx:69` рисует локальный canvas 700×500 с полями, рамкой и изменёнными размерами исходного изображения; сервер получает оригинальный файл. SVG показывает только `generatedCanvasMap` (`:377`), но не загружает сохранённый `background_asset_id` после reload.

Таким образом, локальная подложка исчезает при повторном открытии редактора, а координаты поставленных на ней объектов могут не совпасть с изображением, которое покажет публичный viewer. UI предлагает SVG/DWG (`:347`), хотя API поддерживает JPEG/PNG/WebP; успешность локального FileReader не означает успешную загрузку.

**Исправить:** единая AssetRef-подложка из API и единое преобразование её координат в план; использовать её сразу после upload и после reload. Объявить только поддерживаемые форматы. Проверить import→POI→save→reload→public на одном и том же изображении.

### A06 — P1. Редактор плана и графа реализован частично

**Подтверждено кодом.** `PlanEditor.tsx:120` добавляет стену фиксированным горизонтальным отрезком, room фиксированным прямоугольником, а graph edges — к ближайшему или последнему узлу. Нет полноценного выбора/перемещения вершин, создания произвольного corridor, редактирования/удаления стен, узлов и рёбер. У существующего POI можно менять описание и удалять точку, но нет полного редактирования title/category/position/access node.

Автоматическая связь ближайших POI не учитывает стены и может провести маршрут через помещение без прохода. Это проблема построения графа редактором; серверный Dijkstra корректно обрабатывает переданный граф.

`svgPointFromClient` (`shared/coordinates.ts:3`) линейно масштабирует bounding rect и не учитывает поля `preserveAspectRatio="xMidYMid meet"`. При другом отношении сторон карты и SVG-box координата клика смещается. Предпочтительно преобразовывать через inverse screen CTM. Нынешние тесты не закрывают реальный responsive layout и touch editing.

**Исправить:** минимальный набор select/move/edit/delete для геометрии, POI и графа, явный выбор концов ребра, room/corridor polygons, корректное преобразование координат. Протестировать план с обходом препятствия, изменение POI и нестандартный размер карты.

### A07 — P1. Привязка съёмки и panorama walk не доведена до интерфейса

### A08 — P1. Обработка сохранения расходится с API и может терять новые изменения

**Подтверждено кодом и действующим ответом API.** `App.tsx:694` распознаёт `409`, хотя сохранение документа возвращает **412 VERSION_CONFLICT**, как записано в OpenAPI и backend-тестах. `shared/conflicts.ts` умеет 412, но рабочий save handler его не использует. Conflict banner/reload flow фактически не включаются нужным ответом.

На любой успешный ответ код безусловно заменяет `editorDoc` отправленной серверной версией. Изменения, сделанные во время запроса, могут быть затёрты, поскольку общий save lifecycle и dirty state отсутствуют. Переключение карты также не защищает несохранённый документ. Кнопка publish сначала меняет local document; при отказе сохранения UI может продолжить показывать «Опубликовано».

**Исправить:** состояние `baseRevision / savedDocument / draft / pendingSave`, корректная ветка 412, защита от поздних ответов и сохранение dirty changes. Явно отделить подтверждённую публикацию от локального намерения. Приёмка — две вкладки, редактирование во время медленного save и неудачная публикация.

### A09 — P1. Имитации результата смешаны с рабочим приложением

**Подтверждено кодом.** `AuthView` (`OrganizerDashboard.tsx:37`) при сетевой ошибке/500/403 может сообщить успешный вход без server session. «Регистрация» создаёт только локальный профиль. Но пользователь получает ложное впечатление доступа и сохранения.

Фото-поиск (`:608`) выбирает фиксированный POI после FileReader. «ИИ-чертёж» в PlanEditor — обычная отрисовка изображения. Offline toggle не создаёт cache; аналитика использует фиксированные числа. **Исправить:** явный отдельный demo mode/fixtures, рабочий auth только по server session, ошибка вместо фальшивого результата, удалить недействующие backlog-контролы из рабочего контура. Демо-учётку разрешать только в явно локальном окружении. Logout не должен безусловно заявлять успех при неотозванной серверной сессии (`App.tsx:1094`).

### A10 — P1. Комплект развёртывания не содержит frontend

### A11 — P1. Нет проверки сквозного продукта

### A12 — P1. Загрузка медиа может блокировать HTTP-процесс и превышать лимит памяти до проверки

**Подтверждено кодом; нагрузочное воспроизведение не выполнялось.** `storage.py:129` сначала делает `await request.body()`, затем проверяет размер. Для upload asset это допускает накопление всего тела до отказа. Capture upload уже имеет streaming bound в `modules/capture/uploads.py`, но media asset upload его не использует.

`routers/media.py:58` — async endpoint, внутри которого Pillow декодирует и создаёт WebP-варианты синхронно. Capture endpoint тоже синхронно нормализует кадр и делает файловый I/O внутри async path и write transaction. При больших допустимых файлах event loop занят обработкой, а запись SQLite удерживает глобальный writer lock.

**Исправить:** общий ограниченный streaming multipart reader, дешёвые проверки до декодирования, thread pool/отдельный image service для CPU-операций; короткая транзакция после подготовки файлов с повторной проверкой ownership/state. Подтвердить ограничение memory и доступность health/public API при параллельной загрузке. Hugin уже отделён от HTTP, это решение сохранять.

### A13 — P2. Preview может открыть другую панораму; округление yaw нарушает контракт

**Исправить:** выбирать asset строго по ID и использовать URL этого ID/состояние loading, обновлять asset registry при upload; повторно нормализовать после округления. PannellumViewport также должен подписываться на асинхронное событие `error`, а не только ловить исключение создания viewer и `load` — иначе HTTP/WebGL failure может оставить индикатор загрузки.

### A14 — P2. HTML-код embed не экранирует название

**Подтверждено кодом.** `OrganizerDashboard.tsx:513` вставляет `mapDoc.title` непосредственно в `title="..."` HTML-строки. Название с кавычкой может изменить структуру iframe при вставке на внешний сайт. Отображение этой строки самим React не является XSS; риск возникает при использовании сгенерированного кода как HTML.

**Исправить:** создавать iframe через DOM API/корректный HTML serializer либо экранировать значения атрибутов, проверить кавычки и угловые скобки. В поставке не задана политика CSP/frame-ancestors: разрешение внешнего embed должно быть сознательно ограничено публичными страницами, а editor защищён от встраивания. Добавить проверку на двух origins без third-party cookies.

### A15 — P2. Есть пробелы в проверке документов и переводе ошибок БД

**Воспроизведено.** Room с точками `(0,0),(100,100),(0,100),(80,0)` имеет самопересечение и ненулевую signed area; API принимает его с 200. В `maps.py:80` есть `_segments_intersect`, но валидатор его не использует. Проверки площади недостаточно для простого полигона.

Повтор ID shape из одной карты в другой даёт **500 INTERNAL_ERROR**, поскольку глобальный PRIMARY KEY сталкивается с отсутствием проверки такого конфликта. Сохранение второй карты откатывается, revision остаётся 1 — атомарность работает. Ошибку нужно переводить в контролируемый 409/422, не раскрывая чужую карту.

Публикация документа с одним POI без плана/графа разрешена. Это **не доказанное нарушение конкретного OpenAPI-правила**: нынешний gate требует только POI. Но стоит определить продуктовую минимальную пригодность публикации и предупреждения об отсутствии навигации.

**Исправить:** проверка простоты полигонов и осмысленные integrity errors; явный publish readiness. Не заставлять автоматически генерировать маршруты там, где организатор ещё не задал граф.

### A16 — P2. Защита auth от enumeration реализована не полностью

**Воспроизведено:** для неизвестного email вызов `verify_login_password` отсутствует. В `routers/auth.py:45` условие `row is None or ...` обрывает вычисление до dummy Argon2, хотя helper специально предусмотрен в `auth.py:68`. Время ответа может различать существующие и отсутствующие аккаунты.

Rate limit хранится в памяти процесса; check и record разделены вычислением пароля. Он не является общей защитой для нескольких процессов, а множество ключей не очищается фоново. Для небольшого одного процесса это базовая защита, но не завершённая политика против параллельного перебора.

**Исправить:** выполнять одинаковую проверку для известного/неизвестного пользователя; согласовать limiter с числом API-процессов и proxy IP; ограничить память. Сохранить уже работающие HttpOnly cookie, CSRF, Origin и ownership.

### A17 — P1. Зависимости требуют обновления, CI не повторяет поставку

**Проверено npm audit 24.10.2026.** Затронуты runtime `pannellum` 2.5.6 и dev/test-цепочки Vite, Vitest, esbuild, @vitest/mocker, tinypool. Для Pannellum есть advisory [GHSA-8423-w5wx-h2r6](https://github.com/advisories/GHSA-8423-w5wx-h2r6), для Vitest — [GHSA-5xrq-8626-4rwp](https://github.com/advisories/GHSA-5xrq-8626-4rwp). Registry предложил обновления Pannellum 2.5.7, Vite 6.4.5, Vitest 3.2.7; версии следует повторно проверить при исправлении.

Critical в отчёте dev/test dependencies **не доказывает удалённое выполнение кода на production API**. Текущие custom tooltip labels используют `textContent`, поэтому эксплуатация именно Pannellum через нынешний UI также не доказана. Но оставлять известные уязвимые версии без проверки не следует.

Lockfiles существуют: npm lockfileVersion=3 согласован с package.json; Docker использует hash-pinned `requirements.lock`. При этом CI устанавливает Python из `requirements.txt` (`ci.yml:66`) и frontend через `npm install` (`:80`). Проверка может пройти на зависимостях, отличных от принятого lock/образа. Python-зависимости дополнительно продублированы в pyproject.

**Исправить:** обновить затронутые пакеты с регрессией viewer/build, использовать `npm ci` и один hash-locked backend-набор в CI/образе; включить SCA для обоих стеков. Сделать пересборку backend-test явной частью проверяющей команды, чтобы старый образ не давал ложный зелёный результат.

### A18 — P2. «Контрактная проверка» не проверяет фактический контракт приложения

**Подтверждено кодом.** `scripts/check_contracts.py` проверяет структуру ссылок и несколько инвариантов схемы/manifest. Он не сравнивает `CONTRACTS/types.ts`, модели Pydantic, реальные request/response/status codes и runtime OpenAPI. Большинство роутеров возвращают dict без response_model.

Например, MapDocument в OpenAPI не описывает несколько фактических ограничений строк и размеров списков, которые вводит Pydantic; login документирует не все реально возвращаемые ошибки Origin/rate limit. A08 наглядно показывает, что наличие OpenAPI не предотвращает рассогласование потребителя.

**Исправить:** определить каноническую генерацию DTO либо небольшой contract-test на реальные HTTP ответы/отказы и проверку согласованности схем. Не выдавать проверку `$ref` за проверку совместимости. Общую схему хранения не нужно автоматически приравнивать к транспортному DTO.

### A19 — P2. Эксплуатация и диагностика требуют завершения

**Подтверждено кодом/отсутствием процедур.** Файлы assets создаются до SQL commit, заменённые кадры и отменённые результаты могут оставлять сироты. Нет работающего retention/GC для captures, raw media, sessions и orphan assets; `delete_map` удаляет только текущие известные ключи. `list_maps` ограничен 100 без pagination, так что более старые карты становятся недоступны из списка.

`main.py:27` молча подавляет ошибки auto-seed; общий handler 500 не записывает причину. Ошибка worker возвращает организатору большой текст subprocess с внутренними путями. Нет явного процесса миграций/резервного копирования/проверки восстановления, хотя защита от неявного пересоздания базы правильна.

**Исправить:** безопасный GC по committed references с учётом активных операций, quota/retention, пагинация, structured logging и короткие пользовательские ошибки с job ID; документировать backup/restore и миграцию SQLite. Приоритет этих частей зависит от срока хранения и числа организаторов, но их нельзя считать реализованными.

### A20 — P2. Документация, маршруты и переносимость расходятся с кодом

На Windows в этом аудите она не перепроверялась; Linux build успешен. Рекомендация — прямой запуск JS entrypoints через Node или стандартные npm scripts, затем реальный Windows smoke.

Fixtures содержат 16 положительных кадров, 8 incomplete и 16 negative_duplicates, из которых 15 уникальны. Набор unrelated файлами не наполнен; reference ready sphere и тест `backend/tests/stitch/test_stitching.py`, на который ссылается README fixtures, отсутствуют. В capture_samples указан 2024 год, тогда как manifest/имена — 2026; модель устройства неизвестна. Указано разрешение автора, но подробного происхождения и измеренной приёмки швов нет.

**Исправить:** краткий актуальный runbook, единые URL, fixtures manifest с проверкой реальных файлов/хешей и честной историей происхождения; отделить результат аудита на контейнере от приёмки на физическом телефоне.

## 5. Полнота MVP и ТЗ

| 13 | Панорамы на плане: position, ориентация, связь с графом | Частично | Координаты записываются; управляемая привязка/heading не закончены, A07 |
| 14 | POI-hotspots и переходы между панорамами | Частично | Настоящий viewer/editor и directed transitions есть; граничный yaw и выбор asset требуют исправления, A13 |
| 15 | Публичный план, поиск/категории, карточки POI | Реализовано | `PublicSpacePage` загружает произвольный slug и использует данные API |
| 16 | Маршрут A→B по заданному графу и линия на плане | Реализовано | Серверный Dijkstra, public API и PublicPlan; качество самого графа зависит от A06 |
| 17 | Условный виртуальный проход с объяснением gaps | Частично | API/viewer умеют; создание необходимых nav bindings через organizer UI не завершено |
| 18 | Live update без смены URL и закрытие unpublish | Реализовано | В публичном экране polling 15 с/visibility, ETag и 404 revoke; физическое измерение SLA не проводилось |
| 19 | Mobile-first, производительность, доступность | Частично | Responsive UI/варианты есть; touch editing, реальные устройства, загрузка/CDN и поток камеры не приняты |
| 20 | Воспроизводимая поставка общего веб-приложения | **Блокируется** | Backend image собирается, но frontend и HTTPS-путь не включены, A10 |

Итого по этой явной декомпозиции: **6 реализованных пунктов, 11 частичных, 3 блокирующих**. Это не процент завершённых строк кода и не оценка всех пунктов как равноценных. Backend ощутимо ближе к готовности, чем полноценный organizer flow. Продемонстрировать карту с заранее подготовленным JSON и готовой сферой возможно; это не закрывает требование «создать пространство браузером и камерой телефона».

## 6. Оценка правил проекта

**Текущий регламент чрезмерно жёсток для текущего масштаба команды и при этом не обеспечивает проверку главного — работоспособности соединённых модулей.** Правила оптимизируют отсутствие пересечений файлов, но недостаточно контролируют смысл совместной реализации. Дублирующие pipelines и mock-success появились при формально хорошем разбиении по директориям.

### Что стоит сохранить

- Ясное разделение обязательного MVP и backlog.
- Единые семантика API/DTO, координаты, единицы углов, immutable slug и revision.
- Запрет удалять рабочую БД ради тестов; миграции и backup.
- Серверные ownership/CSRF/Origin, authorization-aware media, отсутствие фиктивного успеха stitching.
- Отдельный worker и отсутствие тяжёлой склейки в HTTP.
- Изолированные worktrees при одновременной работе; запрет разрушать чужие изменения и force-push в main.
- Проверки по изменённому поведению, осмысленное review рискованных правок.
- Запрет публикации/взаимодействия с Hub без явного поручения пользователя.

### Что сейчас мешает и почему

| Правило/механизм | Конкретная проблема | Предлагаемое упрощение |
|---|---|---|
| Жёсткие `allowed_paths` для каждой задачи | Для завершения функции часто нужны feature, shared helper и composition root одновременно. Изменение интеграции откладывается или возникает альтернативный код | Владение как routing review, а не полный запрет. Разрешать сопутствующие тесты и минимальную интеграцию с объяснением в PR |
| Запрет shared/app registration до общей финальной интеграции | Features готовы по отдельности, но wiring не проверяется до конца; A07 — прямой пример пропущенной передачи props | Подключать минимальный вертикальный срез в том же PR, сохраняя координацию только для конфликтующих shared changes |
| Обязательное ожидание всех зависимостей перед началом | Часть связей — организационные, а не технические: UI по стабильному контракту можно разрабатывать до merge worker | Разделить зависимости разработки и зависимости приёмки. Mock допустим в тестах; production не должен подменять результат |
| Один PR строго на заранее существующий ID | Маленький интеграционный баг/аудит требует дополнительной регистрации и разрешения путей | Один связный результат на PR; task IDs полезны, но не обязательный пропуск CI |
| WORKPLAN + manifest как два вручную поддерживаемых источника | В manifest завершён только foundation, в workplan открыты все 17 остальных задач, хотя git history содержит их merge | Один источник статусов; второй генерировать или удалить |
| Отмечать завершение только отдельным изменением main после merge | Противоречит запрету работать напрямую на main; требует дополнительного административного шага без ясного владельца | Обновлять статус автоматически по merge либо учитывать его в PR и считать итогом факт merge |
| «Полная синхронизация board проверяется CI» | `check_contracts.py` вообще не читает WORKPLAN. У integration allowed_paths в manifest есть `.github/**`, AGENTS и TASKS, отсутствующие в разделе workplan | Убрать обещание несуществующей гарантии либо генерировать доску из одного источника |
| Исключение для status-only изменений | `.github/check_task_scope.py:64` содержит некорректную regex; простой перевод `[ ]`→`[x]` вызывает re.error | Если checker остаётся, исправить и покрыть его двумя-тремя meaningful tests; лучше убрать status bookkeeping из blocking gate |
| Все проверки и второй участник на любой размер правки | Документация/мелкие UI-исправления получают тот же процесс, что auth, схема и worker | Review и проверки по риску. Не считать обязательным запуск тяжёлой склейки при исправлении текста |
| Обязательный ранний push/Draft PR вместе с запретом публикации без поручения | Агенту приходится разрешать противоречие правил вместо работы | Явно: локальная работа разрешена; push/PR только при авторизации пользователя или установленном командном режиме |
| Закрытое распределение директорий | Известная ошибка Windows build уже зафиксирована в capture README как «вне allowed_paths» и оставлена | Создавать обычный follow-up issue/фикс по обнаруженному дефекту без перепроектирования всей task graph |

Ещё один индикатор потери актуальности: локальный git history содержит интеграционные task-названия, которых нет в manifest. Это не доказывает обход GitHub branch protection — настройки и история checks удалённо не исследовались. Но показывает, что доска уже не описывает фактическую последовательность работы.

### Предлагаемый компактный регламент

1. Источники требований — ТЗ и короткий список MVP acceptance scenarios. Backlog не маскируется работающим функционалом.
2. Ветка на связный результат; отдельная worktree нужна при конкурентной работе, а не как универсальный ритуал для любого чтения/отчёта.
3. Не менять чужие незакоммиченные файлы, рабочие БД и main разрушительными операциями. Публикация требует авторизации.
4. Контрактные изменения отражаются одновременно в схеме, DTO, server/client и проверках; несовместимые изменения требуют согласования владельцев потребителей.
5. Границы модулей определяют ответственность. Минимальные связанные shared/wiring changes допускаются в том же PR; массовые пересекающиеся изменения координируются заранее.
6. У каждой функции есть короткий критерий готовности через реальное приложение. Mock-only тест не закрывает API/worker/browser integration.
7. CI обязателен на merge: воспроизводимая установка из lock, затронутые проверки и общий быстрый smoke. Тяжёлые worker/device tests запускаются для соответствующих изменений и релиза.
8. Независимое review обязательно для auth, schema/migrations, потери данных, worker и существенных контрактных изменений. Для документации и малых локальных правок — сокращённый процесс по политике команды.
9. Единственный учёт задач; статус определяется PR/merge, не двумя ручными файлами. Owners помогают найти reviewer, а не запрещают исправлять интеграцию.
10. При обнаружении проблемы за пределами текущей задачи — зафиксировать конкретный дефект и следующий шаг; не создавать вторую реализацию функции ради соблюдения путей.

Это предложение для следующего изменения правил. В рамках аудита существующие AGENTS/manifest/CI не переписывались.

## 7. Рекомендуемая последовательность исправлений

### Этап 1 — сделать обязательный путь честным и воспроизводимым

1. Исправить A01/A02: camera stream, terminal session и доставку последнего кадра/результата. Добавить тест реального DOM lifecycle video и browser smoke камеры.
2. Исправить A03/A04: одна pipeline, измеренные метаданные, lease/heartbeat/cancel. Реальная положительная и отрицательная серии должны войти в тесты worker.
3. Исправить A10/A11: поставка frontend, HTTPS runbook, реальный сквозной тест. Его минимальная цепочка: login → новая карта → импорт → POI/граф → съёмка/склейка → панорамы/hotspots → publish → visitor route/walk → live update → unpublish.
4. Убрать ложный успех и production demo fallbacks A09, исправить 412 и save lifecycle A08. Сразу обновить зависимости A17 и зафиксировать совпадающую установку в CI/образе.

### Этап 2 — закончить редактор и убрать архитектурные причины ошибок

1. Завершить A05–A07: сохраняемая подложка, операции геометрии/графа, panorama position/node/heading.
2. Вынести из App session и organizer workspace; общий документ, asset registry, save state и capture state получают понятных владельцев.
3. Объединить media processing, выделить map service из роутеров, устранить A12–A16.
4. Включить проверки настоящего контракта, escaping embed, missing media, отрицательных upload/saving сценариев.

### Этап 3 — принять продукт на устройствах и облегчить процесс

1. Проверить iOS Safari/Android Chrome по HTTPS: 16 кадров, отказ камеры/датчиков, retake, сеть, retry/cancel, панорамы и touch редактор.
2. Измерить время первой карты/preview, response health при загрузках, live update, память worker и качество швов. Зафиксировать устройства, версии, условия сети и фактические цифры.
3. Проверить внешний iframe, отзыв публикации/медиа, резервное копирование и восстановление; закрыть A19/A20.
4. Упростить регламент по разделу 6, синхронизировать документацию с реальным приложением. Не тратить следующий цикл на backlog, пока эти проверки не пройдены.

Критерий завершения: новый организатор создаёт пригодную карту и панорамный маршрут через документированные экраны на телефоне; нет ручного редактирования SQL/JSON, подмены склейки готовой сферой и сообщения об успехе после ошибки. Отдельная загрузка готовой сферы остаётся самостоятельным рабочим сценарием и способом восстановления.

## 8. Воспроизводимость дополнительных наблюдений

Стандартные команды приведены в разделе 2. Для локальных дополнительных проверок были использованы следующие команды из корня (вспомогательные файлы находятся в `/tmp`, не являются частью постоянного набора тестов):

```sh
docker compose --profile test run --rm -T -v /tmp/ttkmap-audit-probes:/audit:ro backend-test python /audit/probe.py
frontend/node_modules/.bin/vitest run --config /tmp/ttkmap-audit-probes/vitest.config.mts
docker compose --profile test run --rm -T -v /tmp/ttkmap-audit-probes:/audit:ro backend-test python /audit/worker_probe.py
docker compose --profile test run --rm -T -v /tmp/ttkmap-audit-probes:/audit:ro backend-test python /audit/worker_probe.py negative_duplicates
```

Эти probe tests намеренно подтверждают существующее дефектное поведение; их зелёный результат не является приёмкой функции. При исправлении нужно перенести необходимые сценарии в репозиторий и изменить assertions на правильное поведение.

Краткие шаги для повторения без временных файлов:

- Камера: смонтировать CaptureGuide с mock getUserMedia, снять/оставить кадр, сравнить `srcObject` video до и после review; затем повторить с настоящей камерой.
- Capture restart: создать сессию, отменить, активировать камеру и снять снова; проверить создание нового capture ID.
- Геометрия: отправить через PUT document room с четырьмя координатами из A15; ожидаемая до исправления реакция — 200.
- ID collision: в две принадлежащие пользователю карты отправить shape с одним UUID; второй запрос вернёт 500 при сохранённой исходной revision.
- Worker: загрузить 16 реальных fixture кадров, уменьшенных до 600×800, вызвать stitch и один цикл `process_one_capture`; сопоставить размеры full.webp и метаданные asset, затем повторить с negative_duplicates.
- Scope checker: вызвать `is_task_status_only_change` для WORKPLAN, подменив `git_file` строками `- [ ]`/`- [x]` одного task ID; ошибка возникает уже при компиляции regex.
- Yaw: `clampHotspotAngles(179.96, 0).yaw` возвращает 180; schema допускает только значение меньше 180.
- Asset: вызвать `pickPanoramaAsset` для отсутствующего ID при наличии другой панорамы; возвращается другой asset.

Результаты относятся к указанному коммиту и окружению. Они не заменяют последующую повторную приёмку после исправлений.
